### 2. Gate false-positive (not a genuine privacy violation) — `tests/sentinel/privacy-sweep.sh` FAILs on the word "plausible" in prose
**Epic:** E11 (handover)
**Reproduction:**
```
bash tests/sentinel/privacy-sweep.sh
# ✘ FAIL — no analytics/telemetry SDK
# ./tests/sharding.ts:163: ...never returns a plausible shard...
# ./frontend/lib/shardHandover.ts:90: ...never returns a plausible-looking shard.
```
The sweep's analytics-SDK regex includes the literal substring `plausible`
(matching the *Plausible Analytics* product name, e.g. `plausible.io`). This
round's new handover code uses the English word "plausible" twice, in comments/
test descriptions only ("never returns a plausible-looking shard" /
"never returns a plausible shard"), describing corrupted-input handling — not a
reference to any analytics product. I manually re-ran the same analytics regex
**without** the bare `plausible` alternative across the whole repo (excluding
node_modules/.git/build/target/.next/reports) and found **zero** hits anywhere
— confirming there is no Plausible Analytics (or any other analytics/telemetry
SDK) import anywhere in the codebase, this round or previously. I also grepped
directly for `plausible\.io`, `<script`, and any import of an analytics package
in `package.json`/`frontend/package.json`: none found.
**Judgment:** this is a **false positive in the gate script**, not a Layer D
privacy-invariant violation — the underlying invariant ("nothing may phone
home") holds. Per Sentinel's own spec I do not weaken or edit the gate to make
this pass; I report it as-is. **Practical consequence:** as written, this gate
is a **hard, non-`continue-on-error` CI job** (`.github/workflows/sentinel.yml`,
"Layer D — privacy & Traditions sweep") — pushing this round's diff as committed
would turn that CI job red and block merge, for a reason unrelated to privacy.
**Recommendation (for the main agent, not applied by Sentinel):** anchor the
regex to the product's domain/token shape (e.g. `plausible\.io|plausible-
analytics`) instead of the bare word, so future prose using ordinary English
("plausible", "implausible") does not collide.

## Verdict rationale

The security fixes themselves are real and correct: I independently rebuilt the
program natively (66 instructions, `.so` = 1,189,664 bytes, matching the
claimed numbers exactly), and — once the test harness is pointed at a local
validator by hand — all 80 tests pass natively, including new tests that prove
the two CRITICAL federation bugs and the HIGH member-recovery bug are fixed.
The new Epic 11 handover code is honest, keeps a shard off the network by
construction, and puts the required warning on the screen. However, the round
also quietly changed a one-line setting in `Anchor.toml` that breaks the
project's own documented way of running its tests — `anchor test`, `make
test`, and `scripts/test.sh` all now fail before a single test runs, because
they try to deploy to the real Solana devnet (where the project's wallet does
not have enough funds) instead of a disposable local test network. Nobody
wrote down that this was an intentional change, so by this project's own rules
that counts as a regression serious enough to fail the round, even though the
underlying security work is sound and just needs one line changed back (or one
flag added to the test scripts) to be fully green and reproducible again. On
top of that, the automated privacy checker flagged a false alarm — the English
word "plausible" in a test description, not a real tracking tool — which I
verified by hand is not an actual privacy problem, but as configured it would
still turn the project's safety-net checks red today. Finally, three of the six
security fixes shipped this round — including one the audit document claims is
tested — have no automated test proving they keep working, which is a gap that
must close before the next round.
