### Finding 1 (HIGH, not CRITICAL) — F63 mailbox `get` does not require the recipient's signature

Task scope item 5 asked specifically: *"The mailbox route must not allow
reading/deleting another user's mail without the recipient signature."*
**Deletion is correctly gated** — `ack` in `frontend/app/api/mailbox/route.ts`
verifies `nacl.sign.detached.verify(ackSignedBytes(to, ids), sig, wallet)`
against the wallet whose published bundle's IK hashes to the mailbox id
(route.ts:227-243). **Reading is not.** The `get` case (route.ts:198-217)
takes only `{ to }` — a 32-hex-char mailbox id — and returns every envelope in
that box (ciphertext, ephemeral pubkey, timestamps) with **no signature
check at all**. Confirmed at the client: `fetchMailboxMessages` in
`frontend/lib/mailbox.ts:169-177` calls `post("get", { to })` and never signs
anything for that call. The mailbox id is not a secret an attacker must
brute-force: `case "bundle"` (route.ts:163-174) resolves any base58 wallet
address to its published `PrekeyBundle` with no auth either, and
`mailboxIdFromIk` is a pure, public hash — so anyone who knows a member's
**public** wallet address (wallets are public keys; nothing here is
membership-gated) can derive their mailbox id and then repeatedly fetch that
member's raw envelope list. Content stays protected (NaCl `box`, so the
ciphertext is opaque) and sealed-sender means the *sender* is never
recoverable without the recipient's SPK secret — so this does **not** trip
Layer D's strict adversarial assertions 3 ("message content or who-messaged-
whom metadata") or 7, which is why this is graded HIGH rather than CRITICAL.
But it is a real gap against the exact requirement this round was asked to
verify, and against the module's own honesty framing: `mailboxCrypto.ts:23-24`
says *"The relay can see which mailbox receives mail and when"* — true, but
incomplete, because the code makes that same view available to **any**
caller of the public API, not only the relay operator. A member's receive-
timing and receive-count are therefore observable by any third party who
knows their wallet address, indefinitely, subject only to the 30-req/min
per-IP rate limit. Recommend: require the same recipient-signature proof on
`get` that `ack` already performs (a signed `{to, ts}` challenge is enough —
no interactive round trip needed) before calling F63 v1 done.
Reproduction: `curl -s -XPOST http://localhost:3000/api/mailbox -d
'{"op":"bundle","wallet":"<victim base58>"}' ...` → derive `mailboxIdFromIk`
→ `curl -s -XPOST .../api/mailbox -d '{"op":"get","to":"<derived id>"}'`
returns the victim's full envelope list with **no proof of ownership
required**.

### Non-finding, explicitly checked and confirmed sound: the relayer allowlist

`frontend/lib/relayPolicy.ts` was read end to end. The policy pins an exact
8-byte Anchor discriminator, exact account count, exact data length, and
requires the fee-payer to sit at a fixed index as the **only** signer — any
other account marked `isSigner` is refused outright (`relayPolicy.ts:107-111`).
This structurally prevents relaying any authority-bearing instruction (seat
votes, membership issuance, treasury moves, migrations) because all of those
require a second live signature the relayer will not provide, and prevents
targeting an unlisted instruction or a tampered payload of a listed one.
`tests/relayer.ts`'s discriminator/account-count assertion is checked against
the **freshly built IDL** (not a hardcoded copy), so drift between the
allowlist and the real program would fail loudly; its refusal-matrix test
explicitly tries a real `withdraw_treasury` instruction, a swapped payer, a
smuggled extra signer, wrong account count, wrong data length, a garbage
pubkey, and truncated data — all seven refused. The on-chain half is proven
live: `send_message` accepted with the relayer as sole signer and the
member's wallet in no account slot. This check passes cleanly — no CRITICAL
found here.

## Verdict rationale

Nothing that used to work broke. I rebuilt the program from a clean state,
ran the project's own documented `anchor test` with no special flags against
a real local validator, and got 100 passing / 0 failing — the exact number
this round's own commit note claims, independently reproduced rather than
taken on faith, including all three brand-new test files for the anonymity
layer (root/epoch mechanics, the relayer's refusal matrix and a live
third-party-fee-payer transaction, and the mailbox's sealed-sender crypto).
The zero-knowledge proof keys still match what the browser and the on-chain
program each expect, and the automated privacy/rank-and-score checker is
still clean. I specifically hunted for the two things this round's brief
worried about most: whether the new relayer could be tricked into paying for
something it shouldn't (I read the policy and its test line by line — it
cannot; it refuses any instruction that needs a second real signature, which
rules out anything with authority), and whether the new mailbox could leak
who is talking to whom (the message content and the identity of the sender
both stay genuinely hidden, verified by test). What I did find, and what
this report leads with, is narrower but real: the mailbox's "fetch my mail"
operation never checks that the caller actually is the recipient — only
deleting mail is signature-checked, not reading it — so anyone who knows a
member's public wallet address can, right now, pull that member's raw
(still-encrypted) mail-arrival pattern without ever proving they own that
mailbox. That does not expose a single word of any message or reveal who
sent anything, so it does not cross the platform's hardest privacy lines,
but it falls short of the specific promise this round was built to keep, and
it should be closed before this feature is called finished. Separately, the
project's own tracking checklist was not updated to list this round's five
headline features even though they are genuinely tested elsewhere, and the
"72 instructions" the team is citing is actually 71 by two independent
counts — both are honest bookkeeping slips, not hidden problems, and neither
changes what the software actually does. None of this touches the
sponsor-recovery guarantees from Epic 11, which I re-checked from scratch and
confirmed the new code never went near them. Given a clean build, 230
passing automated checks, and no violation of any of the platform's hard
privacy rules, but with one real and specific new-surface gap plus an
undercounted coverage checklist, the honest call is **pass, with warnings**
— not a clean pass, and not a failure.
