2. **No shard on any server — HOLDS.**
   No network sink of any kind (`fetch`, `XMLHttpRequest`, `WebSocket`,

   `sharding.ts`, `shardCustody.ts`, or `recovery.ts` — confirmed by full-file

   (`localShardCustody`) is the only concrete custody implementation shipped

   only the definition file itself), so there is no other code path yet that
   could route a shard to a server.

3. **No structure links a shard to a member — HOLDS.**
   `shardCustody.ts:20-34` (the `ShardCustody` interface) and its
   `localShardCustody` implementation (`shardCustody.ts:52-66`) store exactly
   one thing per entry: an opaque base64 blob (`b64(sealed)`), under a storage
   key that is itself `"shard:" + SHA-256("aha-shard:" + code)` truncated
   (`shardCustody.ts:45-50`) — never the raw one-time code, never a name,
   wallet address, public key, identity commitment, or timestamp. A full dump
   of `localStorage` under this scheme yields key/value pairs of
   `hash → opaque-blob`, nothing else; the comment block at `shardCustody.ts:1-18`
   states this is deliberate, and the code matches the claim.

4. **No enumeration path — HOLDS.**
   `ShardCustody` (`shardCustody.ts:21-34`) declares exactly three methods —
   `put`, `get`, `burn` — and an explicit comment (`shardCustody.ts:31-33`)
   records the omission of `list()/keys()/count()/entries()/has()` as
   intentional. `localShardCustody` (`shardCustody.ts:52-66`) implements only
   those three. Verified statically both by my own read and by
   `tests/sharding.ts:129-138` ("ShardCustody exposes no enumeration path
   (static)"), which strips comments and asserts the *code* (not the prose)
   contains no `list|keys|count|entries|iterate|values|has` method — re-ran,
   passes.

5. **Fast path requires a genuine member shard — HOLDS, with one architectural
   note.** `recoverMemberPresent` (`recovery.ts:29-33`) throws unless
   `mine.role === "member"` and `sponsor.role === "sponsor"`; two sponsor
   shards passed as `(sponsorShard, sponsorShard)` are rejected — proven by
   `tests/sharding.ts:70-80`, re-ran, passes. **Note, not a fail:** Shamir
   shares are cryptographically indistinguishable by design (`sharding.ts:36-38`
   says so explicitly: "the roles live in custody/handover, not in the shard
   bytes"), so this guard is a caller-declared-role check, not a
   cryptographic proof that a given byte string *is* the member's own shard.
   The code is honest about this — the true enforcement point is meant to be
   the in-person handover/custody layer (F74, not yet built) that decides
   which shard the calling code is allowed to label `"member"`. As implemented
   today, the function does exactly what the backlog line asks ("two sponsor
   shards CANNOT masquerade as member-present") and no more; I record the
   deeper architectural dependency on F74 as a coverage gap below, not as a
   Layer F failure — the assertion is about this function's behavior, and it
   behaves correctly.

7. **Shard freshness — HOLDS.** `reshareMaster` (`recovery.ts:89-94`) always
   cuts a fresh 3-of-3 set via `splitFresh(master)` from the reconstructed
   master, with no code path that reuses an old shard. `tests/sharding.ts:102-113`
   ("re-sharding cuts a fresh, incompatible set") explicitly tests that an old
   shard combined with a new one does **not** silently reconstruct the master

   lifecycle (burn-then-reissue after any sponsor-shard recovery, key
   rotation, or holder replacement); the burn call itself is a caller
   responsibility using `ShardCustody.burn` (present, idempotent per
   `shardCustody.ts:28-30`) — the module gives the caller everything needed to
   do this correctly.

8. **Challenge window — HOLDS.** `CHALLENGE_WINDOW_MS = 7 * 24 * 60 * 60 * 1000`
   (`recovery.ts:12`) is a module-level constant. `openSponsorRecovery(code, now)`

   `(code: string, now: number)` — so there is no client-suppliable value that

   `intent.windowMs`, which can only ever have been set to the constant.
   `tests/sharding.ts:82-100` exercises "too early → refused",
   "cancelled → refused", "after window, not cancelled → succeeds" — re-ran,
   passes. The intent object (`RecoveryIntent`, `recovery.ts:40-44`) is a

## Verdict rationale
This was a focused check of one new piece of the system: a way for two of the
three key-holders (you, and either of your two sponsors) to rebuild your
secret if you lose your device — without that rebuilding ever touching the
public blockchain or any server. I read every line of the three files that
implement this, tried to break each of the nine specific promises the team
wrote down for themselves, and re-ran their own automated tests fresh rather
than trusting their word that the tests still pass. All nine promises hold.
Nothing here can phone home, nothing here lets a device holder learn who else
they're storing a shard for, and a member with only one sponsor (not yet fully
admitted) correctly gets told "no" rather than a false sense of protection.
The only things I flag are not broken promises but *not-yet-kept* ones: this
piece isn't connected to the onboarding screen or a real handover flow yet, so
what I verified is that the building block is sound, not that a member could
use it today end to end. I also re-ran the standing privacy checks from prior
rounds to make sure this new work didn't quietly reopen an old wound, and it
did not. Verdict: PASS.
