## The five claims under scrutiny (task brief), verified against commit `64c936d`

1. **"No enumeration surface was ADDED."** — **CONFIRMED.** Read
   `programs/ayni/src/state.rs` field-by-field: `OwnerTag { membership: Pubkey,
   bump: u8 }` — no authority/granter/recipient field. `VisibilityKeyDrop {
   sealed: [u8; 104], epoch: u16, bump: u8 }` — no authority, no membership, no
   granter/recipient. `MemberProfile` is keyed `["mprofile", circle,
   commitment]`, commitment-keyed like `VisibilityPolicy`, no wallet field.
   `bash tests/sentinel/privacy-sweep.sh` (5/5) and a manual grep for
   `score|rating|rank|karma|tier|badge|count` across the three new structs:
   no hits.
2. **"Hidden ≡ absent holds on the read path."** — **STRUCTURALLY TRUE, BUT
   PRACTICALLY FALSE AS SHIPPED IN `64c936d` — this is Regression 2, CRITICAL.**
   `MemberProfile.bio_ct` genuinely is fixed-length (`200` bytes,
   `MemberProfile::BIO_CT`), always written by `upsert_member_profile`, and the
   frontend read path (`openMemberProfile`/`getTrustPage`) decides by
   decryption, not by a "may I?" branch — confirmed by code read. **But** the
   write path itself, as shipped, could not be exercised by the one class of
   member the whole feature exists for: a shielded member. `payer = member` in
   both `upsert_member_profile` and `shield_membership` forced the
   zero-balance derived key to pay its own rent. Reproduced **three times
   independently** (once in the prior round's two fresh-validator runs, once
   more this round on a third, freshly-built, freshly-deployed local
   validator): `tests/epic5.ts` → `Transfer: insufficient lamports 0, need
   3473040`, four cascading failures in the same `describe` block. So the
   structural claim ("the bytes are ciphertext, always the same shape") is
   sound; the operational claim implicit in shipping it ("a shielded member can
   actually publish and be read") was false in `64c936d`.
3. **"`Membership` layout is byte-identical... `findMyMemberships` still
   resolves legacy memberships."** — **CONFIRMED.** `git diff d6ab0e3 64c936d
   -- programs/ayni/src/state.rs` shows zero lines changed *inside* the
   `Membership` struct — only additions elsewhere in the file. `findMyMemberships`
   (`frontend/lib/member.ts`) unions a derived-address lookup
   (`findShieldedMemberships`, gated on a cached viewing secret) with the
   original `memcmp`-on-`owner` legacy query; both branches read and are
   exercised in `tests/epic5.ts`'s "leaves a plain membership enumerable by
   wallet" / "still lets the member resolve their own membership" cases,
   confirmed still passing on both runs this round.
4. **"`shield_membership` cannot brick a membership and cannot be called by a
   stranger or a Council seat."** — **CONFIRMED.** Code read of
   `programs/ayni/src/instructions/shield_membership.rs`: authorisation
   requires `who == membership.owner` when an owner is set, or
   `membership.is_member_key(&who)` for an anonymous membership — no bypass.
   Dropping `owner` to `Pubkey::default()` is refused unless a guardian
   remains (`MembershipWouldBeUnusable`), so it cannot strand a membership.
   The `ShieldMembership` account struct carries **no Council/seat account at
   all** — structurally, a Council seat has no code path into this
   instruction unless it happens to also be the membership's own
   owner/guardian, which is not a Council-seat bypass. `tests/epic5.ts`
   exercises both the stranger and the Council-seat cases directly
   (`expectFail(..., "Unauthorized")`), unaffected by this round's other
   findings.
5. **"`/board` renders nothing and issues no post query to an unconnected
   visitor."** — **CONFIRMED.** `frontend/app/board/page.tsx`:
   `useEffect(() => { if (!connected) { setCircles([]); setPosts(null); return;
   } listCircles().then(setCircles); }, [connected])` — `listCircles()` (the
   query that would enumerate Circles/posts) is never called while
   disconnected, and no other effect fires a post query independent of
   `circles`.

## Verdict rationale

This round set out to check five specific claims made about the shielded-membership
work in commit `64c936d`, and four of the five hold exactly as claimed: nothing
new can be listed or grouped by wallet, the account layout did not change, the
shielding instruction cannot be hijacked or used to lock someone out of their
own membership, and the public bulletin board now genuinely shows nothing to a
stranger. The fifth claim — that a hidden bio looks the same as no bio at all —
is true in the data itself, but the feature that was supposed to deliver it
could not actually be turned on: the very key a shielded member needs to sign
with had no money in it and nothing gave it any, so writing a profile failed
every time it was tried. That is exactly the kind of failure this project's
own rule exists to catch, because the natural workaround — sending money to
that key from the member's real wallet — would have tied the two together more
tightly than before, not less. Together with an already-known, separate
problem in the voting code (a single seat could push through a Council
appointment or move treasury money without a real vote), this is why the round
fails: both were live on the actual public network anyone can use, not just in
a test file. The good news is that both were fixed correctly and thoroughly
while this review was underway, and this report independently checked the live
network and confirmed the fixes are the ones actually running, not just words
in a commit message. The remaining concern is process, not code: those fixes
were pushed and put live before this review had said anything, for the second
time in one day, on the very afternoon the first time was flagged. Good fixes
delivered outside the review process the project agreed to still count as
outside the process, and a mechanical brake on that — not another promise to
wait next time — is the outstanding piece of work.
