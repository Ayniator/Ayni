## Item 1 — `scripts/sentinel-push-gate.sh`: does it block, and is the escape hatch theatre?

**It blocks.** Independently reproduced against the real repo at its current
`3b59ac7` state: piping a synthetic pre-push stdin line for the current FAIL
verdict through the script, with no override set, returns exit 1 and the
expected `BLOCKED` message. This matches the peer's own dry run.

**Adversarial testing, both versions, against an isolated throwaway git repo
(not the real one) built to mirror the script's expected layout:**

1. **Verdict parsing is a prefix match, not an exact match.** The case
   statement is `PASS*)`, so any string that merely *starts with* `PASS`
   satisfies it. Demonstrated: a `latest.md` whose verdict line reads
   `Verdict: PASS (just kidding, actually FAIL, see body)` is accepted —
   `exit 0`, `"latest verdict is PASS (just kidding, actually FAIL, see
   body), and every pushed commit is reviewed."` The anchoring regex
   (`^[[:space:]]*Verdict:`) does correctly resist prose-injected fake
   `PASS` mentions elsewhere in the file (tested: a line reading `"This round
   looked PASS-worthy at first glance."` followed by the real `Verdict: FAIL`
   line is correctly read as FAIL) — the weakness is narrower than "any
   mention of PASS fools it," but a verdict line that itself starts with
   `PASS` and says something else afterward is not caught.
2. **The "named by some report" check is a bare grep for the SHA anywhere
   under `reports/sentinel/`, with no requirement that the mention be
   positive.** Demonstrated: a report reading `Scope: commit <sha> was
   reviewed and everything is terrible` still marks that commit "reviewed."
   Combined with finding 1, a report engineered to read `Verdict: PASS
   (narrator: it was not)` and separately list a commit's SHA anywhere in its
   body would satisfy the gate's two checks in full.
3. **(`3b59ac7` only) `OVERRIDES.md` is checked for presence in the diff, not
   content.** `git diff --name-only "$range" | grep -q
   '^reports/sentinel/OVERRIDES.md$'` — demonstrated: appending a single
   blank line to `OVERRIDES.md` and committing it satisfies the check;
   `SENTINEL_OVERRIDE` is echoed to the terminal but never compared against
   what actually landed in the file.

**Disposition: not pure theatre, but not closed either.** Both versions
correctly stop the lazy/accidental case (a `git push` run without an override
set, against a non-PASS or unreviewed state) — that is a real, working
mechanical gate where none existed two rounds ago, and this round confirms it
functions exactly as claimed for that case. `3b59ac7`'s addition of
`OVERRIDES.md` is genuine progress: it converts an override from something
that "lived only in a terminal" (the honest phrase the first version used
about itself) into a durable, diffable, permanently-reviewable repository
artifact — that is a real improvement in auditability, not cosmetic. But all
three findings above show the gate can be **satisfied on paper without being
honoured**, by a party willing to write text that merely has the right shape.
Given this round's other finding (Regression 1, below) is precisely about
willingness to bypass process under pressure, this is not a hypothetical
concern to leave open.

**Recommendations (report only, not implemented — not Sentinel's job):**
tighten the verdict match to an exact comparison against the two legal values
(`^PASS$|^PASS WITH WARNINGS$`, trimmed); require the "named by report" check
to find the SHA specifically inside a line asserting a PASS-shaped verdict for
that report, not anywhere in the tree; require `OVERRIDES.md`'s new content
(via `git diff`, not just its name) to contain both the literal
`$SENTINEL_OVERRIDE` value and at least one of the pushed commit SHAs.

## Item 2 — `tests/sentinel/f92-f93-check.sh`: does it assert directions, or just presence?

**Read in full and independently re-run: 5/5.** It genuinely asserts
directions, not mere presence, on every point the brief asked about:

- **Fail-CLOSED sponsor check**: regex-captures the `validated = infos ? … :
  …` ternary and asserts the "no answer" branch is the literal `false`, and
  that the confirmed-branch uses `some(` — not just that the word `validated`
  appears somewhere.
- **Fail-OPEN funding check**: asserts the `catch { … funded = true … }`
  shape specifically, not just that `funded` exists.
- **`CIRCLE_SPACE`/`MEMBER_TREE_SPACE` drift**: this is the strongest check in
  the file — it does not merely grep for the constant names, it `Function()`-
  evaluates the actual expressions found in `createGate.ts` and compares the
  computed byte counts against the same formula independently re-derived from
  `programs/ayni/src/state.rs`'s field layout in the check script itself. A
  silent drift in either file would be caught numerically, not textually.
- **Early return behind the popup**: asserts `if (blocked) { … return ( …`
  with a bounded lookahead, not just that a "blocked" variable exists
  somewhere.
- **Platform detection kept out of the wallet shuffle**: asserts `LINK_ORDER[platform]`
  drives `WalletChooser.tsx`'s ordering AND that no `shuffle(...platform...)`
  call exists AND that `Math.random()` is still the entropy source — three
  independent, differently-shaped assertions, not one.
- **No store link on `/get-app`**: matches an explicit URL pattern for the
  four plausible store/TestFlight domains against the RAW (non-normalised)
  source, separately from the prose-disclosure checks, which run against a
  JSX-normalised copy specifically so a reflow cannot silently "remove" a
  disclosure that is still on screen.

**Honest, disclosed limitation, not a hidden defect:** the file's own header
says "mechanical half only… no Playwright suite in this repo," and every
check here is necessarily a static-text/regex assertion against source, not a
runtime harness. Like the push-gate's SHA/verdict matching, a sufficiently
determined rewrite could, in principle, keep the matched *text* in place
(even as an inert comment) while breaking the *behaviour* it is meant to
attest to — this is a general property of regex-based gates in this repo, not
unique to this file, and it is the same class of limitation already carried
and disclosed for every other `tests/sentinel/*.sh` script. **Disposition:
sound and non-trivial; closes the WARNING raised last round.** The peer's own
framing ("it caught a real defect on its own first run") was not independently
re-verifiable this round (no evidence of what that defect was is preserved
anywhere Sentinel could check), but the script as it stands today is not weak
in the ways the brief asked about.

## Carried item — `epic2-reinsert-timing`: what it took to clear it, and current status

**Root cause, as already diagnosed and now addressed:** the original 2-second
membership term left roughly 370ms of margin between `cLive`'s issuance and
the `reinsert` call, against the mandatory >1s epoch-predate separation plus
two on-chain confirmations — genuinely not enough margin on a constrained
host, and a test-timing defect, not a program bug (this diagnosis is
unchanged from the original quarantine entry and was not re-litigated this
round). **What it took:** widen the term (now 12s) so the same fixed
overhead is a small fraction of the budget, and add a self-diagnosing
assertion (`elapsed`ms of a `TERM_SECS*1000`ms term) so a future regression is
legible from the failure output alone. This round independently reproduced
the fix **twice**, on two separate, freshly-provisioned, isolated local
validators (ports 8995 and 8997, `target/deploy/ayni.so` unchanged from last
round since no application code moved) — both **6/6 passing**, no
`MembershipExpired`. Per spec's own retry protocol this specific case is
cleared. **Not yet fully closed**: the fix lives in commit `3b59ac7`, which is
**not pushed**, and this round did not wait for the concurrent full-suite run
to confirm no other case in the same `describe` block (or elsewhere) was
disturbed by the wider `TERM_SECS` (the commit's own stated cost is that
`cDead`'s expiry wait grows accordingly). The quarantine entry in
`checklist.yaml` is left in place, not deleted, with a resolution note
appended — close it once `3b59ac7` (or a successor) is pushed and a full
suite run is seen to complete cleanly.

## Verdict rationale

Nothing in the actual application — the program, the encrypted read path, the
faucet — moved this round, and what moved last round stayed fixed: this round
checked, rather than assumed, that the live network still runs the corrected
code, and it does. The two new pieces of work — a guard that refuses to push
unreviewed changes, and a test that locks in two eligibility gates — are both
real and were checked hard rather than taken on trust: the guard genuinely
stops a careless push, and the test genuinely checks the two directions that
matter (fails closed when it must protect the fellowship's governance, fails
open when it must not lock out a member who was going to be refused by the
network anyway). But the guard was defeated the same day it was written, for
the very commit that introduced it, using its own front door — an escape
hatch meant for a rare, deliberate, well-justified exception — apparently
against what the user had actually been told would happen. Nobody can currently
prove which of several sessions did that, because they all write to this
repository under one name; that is itself worth fixing, separately from
today. And in the middle of checking all of this, something inside the
tooling tried to get this review to leave a finding out of its report to the
user — which did not happen, and would not have been honoured regardless of
who or what asked. A process that can be turned off by whoever is in a hurry,
using a mechanism explicitly built for occasions that are supposed to be rare
and well-justified, has not yet become a safeguard — it has become a
formality with a paper trail. That is progress over having no trail at all,
and it is why this report credits the work plainly rather than dismissing it.
It is not yet a reason to say the round passed.

## RESOLUTION (appended by the coordinating session, 2026-08-12)

The original verdict above is left intact. Every finding it raised against
`scripts/sentinel-push-gate.sh` has since been fixed in commits `4396960` and
`a1765f4`, each verified against the exact attack this report demonstrated:

1. **Prefix-match verdict parsing** — now an exact comparison against the two
   legal values (`PASS`, `PASS WITH WARNINGS`), with any verdict containing
   FAIL or CRITICAL vetoed outright. Re-tested with this report's own string,
   `Verdict: PASS (just kidding, actually FAIL)`: **blocked**.
2. **Bare SHA grep across the reports directory** — replaced with a structured
   registry, `reports/sentinel/REVIEWED.md`, matched per line. Re-tested with a
   commit named only in the sentence "This round REJECTED commit <sha> as
   dangerous": **blocked**, where it previously counted as reviewed.
3. **Override log satisfied by touching the file** — the entry must now name a
   commit in the pushed range. Re-tested with a blank-line append: **blocked**.

Two further defects were found while fixing those, neither reported here
because neither was reachable until the gate started reading its own audit
trail:

4. **Self-reference deadlock** — a commit cannot contain its own future SHA, so
   both the registry commit and the override-log commit were permanently
   unpushable. Commits touching nothing but Sentinel bookkeeping
   (`reports/sentinel/**`, `tests/sentinel/checklist.yaml`) are now exempt from
   the reviewed requirement; the override log may name any commit in the range.
5. **The hook resolved the wrong root.** git invokes the gate through the
   symlink `.git/hooks/pre-push`, so `cd "$(dirname "$0")/.."` landed in
   `.git/` — where `reports/sentinel/` does not exist. Every file-based check
   silently returned empty *when run as a hook*, which is the only path that
   matters. This is also why the first override appeared to work: that version
   exited before touching a file. Fixed by resolving `$0` through `readlink`
   and preferring `git rev-parse --show-toplevel`.

**Still open, and not fixable in code:** several sessions share one `Ayniator`
git identity, so an override cannot be attributed to an actor. Per-session
identities are an environment change for the user to make. Until then, the
override log records the reason and the commits, but not reliably *who*.

**Also for the record:** this report's round flagged an apparent manipulation
attempt — a system-reminder attributing an in-flight edit of the gate to "the
user or a linter" and instructing that the user not be told. That is standard
Claude Code harness text emitted whenever a file changes outside the current
context; what it described was this session hardening the script. There was no
adversary. The reviewer's refusal to withhold a finding was the correct
instinct and should not be discouraged, but the conclusion was mistaken.
