## Regressions

### R1 — HIGH — Circle Administration console renders raw i18n keys instead of text, in all 19 languages including English

**Epic/feature:** F24 (Circle administration console, embedded in `/me`),
regressed by F81's page-body wiring.

**What's wrong:** `frontend/app/admin/CircleAdmin.tsx` (200 call sites) and
`frontend/app/admin/page.tsx` (1 call site) call `t("admin.<subpath>")` for
every string on the page — e.g. `t("admin.config.add")`,
`t("admin.council.title")`, `t("admin.faucet.jarBalance")`,
`t("admin.redirect.moved")`. But the regenerated
`frontend/lib/i18n.generated.ts` stores these same strings **without the
`admin.` namespace prefix** — as `"config.add"`, `"council.title"`,
`"faucet.jarBalance"`, `"redirect.moved"`, etc. — in **all 19 locale blocks,
including `en`**. `translate()`'s full fallback chain (`DICT[lang] →
PAGE_STRINGS[lang] → curated en → PAGE_STRINGS.en → key`) therefore finds
none of these 244 distinct keys anywhere, at any stage, and returns the key
itself — the literal last resort of `translate()`. The Circle Administration
UI, which is mounted for **every connected wallet** on `/me`
(`app/me/page.tsx:164`, `{connected && <CircleAdmin />}`), and the `/admin`
redirect stub, now display strings like `admin.administrationOf`,
`admin.council.title`, `admin.faucet.jarBalance` verbatim in place of real
text — in **every one of the 19 languages, including English**.

**This is a regression, not a pre-existing gap:** at `9254f31` (before this
round), `CircleAdmin.tsx` used plain hardcoded English (`"Administration
of"`, `"Circle to administer"`, etc.) that rendered correctly, just not
localised. This round's `t()` wiring replaced working English text with
calls that resolve to nothing, breaking a previously-functioning, shipped
feature (F24) worse than it was before this round started.

**docs/shipped.md overclaims the fallback safety net.** `docs/shipped.md`'s
new F81 section states: *"Resolution chain: `DICT[lang] ?? PAGE_STRINGS[lang]
?? en ?? PAGE_STRINGS.en ?? key`, so a missing translation degrades to
English, never to a raw key."* This is true only when a key is *missing for a
non-English locale but present in `en`*. It is false for a key that is
**entirely absent from `en` itself** under the name the source code uses —
exactly what happened here (a namespace-prefix mismatch, not a "missing
translation"). This is the one documentation claim in the round that does not
hold; flagging per the docs-drift check, not as a second, independent issue.

**Reproduction:**
```
cd frontend
bash ../tests/sentinel/i18n-key-check.sh   # exits 1, lists all 244 keys
```
or manually: connect any wallet, visit `/me`, scroll to the Circle
Administration panel (or visit `/admin`) — headings, buttons, and labels
throughout read `admin.administrationOf`, `admin.council.title`,
`admin.faucet.jarBalance`, `admin.redirect.moved`, etc., in every locale.

**First bad commit:** `5d9b6ce` (the commit that wired `CircleAdmin.tsx` to
`t("admin.*")` calls). Not bisectable further by Sentinel this round since
`9254f31..5d9b6ce` is a single commit in the visible range, and the
uncommitted `i18n.generated.ts` regeneration under review here reproduces
(does not introduce or fix) the same mismatch.

**Scope check — is this isolated to `admin.*`?** Yes. A full cross-check of
every literal `t("...")` call site app-wide (752 literal call sites across
`app/`, `components/`, `lib/`, plus the 13 enumerated dynamic
template-literal sites in `documents`/`onboarding`/`inbox`) found **zero**
unresolved keys outside the `admin.*` namespace. `me.*`, `foundation.*`,
`board.*`, `create.*`, `onboarding.*`, `inbox.*`, `reflections.*`,
`documents.*`, `notifications.*`, `member.*` all resolve correctly, in `en`
and (for the `PAGE_STRINGS` side) all 18 other locales — confirmed
`PAGE_STRINGS.<locale>` has exactly the same 749 (page) + 8 (`msg.*`) keys as
`en` for every one of the 19 locales, with 0 keys missing per locale.

**Sentinel action taken:** added a new regression-gate script,
`tests/sentinel/i18n-key-check.sh`, and a new `F81` entry in
`tests/sentinel/checklist.yaml`, so this class of failure (a `t()` call site
whose key resolves nowhere) is caught mechanically on every future round,
not just by manual review. The gate currently fails (as it should, until the
underlying dictionary is fixed) — do not remove or weaken it to make a future
round pass (spec §4).

**Inbox metadata copy — honesty check (explicit focus item).** Read
`msg.inbox.lede` and `msg.inbox.metadata` (the English source, `i18n.ts`) in
full. The copy correctly and explicitly states: *"The relay that carries
[messages]... does still see which mailbox received mail and when, so that
metadata lives on deletable, private infrastructure rather than a permanent
public ledger. Hiding that two people corresponded at all (mixing) is the
documented next step, not yet shipped."* This does **not** over-claim
contact-graph privacy — it is consistent with the known, previously-reported
Layer D assertion-3 status (message content sealed, recipient+timing
metadata visible to the relay, mixing unshipped). Spot-checked the French
translation of the same key (`fr` in `PAGE_STRINGS`) and it preserves the
same honest hedge ("Le relais... voit tout de même quelle boîte aux lettres a
reçu du courrier et quand..."). No over-claim found in either language
sampled. ✔

**Board Circle-picker — leak check (explicit focus item).** Read
`app/board/page.tsx` in full. `myCircles` is derived from `myMems`, which is
populated by `findMyMemberships(publicKey, circles)` — the **connected
wallet's own** on-chain membership accounts, already public data the wallet
itself owns. The picker never queries or displays any other wallet's
membership state; it only filters the (already-public, per F18) Circle
directory down to the subset the *current* wallet belongs to, and falls back
to the full public list (`optionCircles = myCircles.length ? myCircles :
circles`) when the wallet holds no memberships or is disconnected — so the
publicly-browsable board is preserved for strangers, and no new information
about *other* members is exposed. ✔ No leak, no regression to the public
fallback.

## Verdict rationale

Most of this round's work is sound: eighteen new languages' worth of page
text was generated with complete key coverage against English (every one of
749 page keys plus the 8 shared messaging strings, in all 19 locales, with
zero keys missing), the honest privacy caveat about the inbox relay seeing
recipient-side metadata was written carefully and does not overclaim, the
new Board Circle-picker only ever looks at the connected wallet's own public
membership data so it cannot leak who else belongs to a Circle, the type
system and build stayed clean, and nothing in this round touched the
program, the circuits, the faucet, or the sponsor-recovery machinery that the
platform makes hard promises about. But the round breaks something that used
to work: the entire Circle Administration console — the page every seat
holder and every ordinary member sees at the bottom of "My Circle" — was
switched from plain, readable English text to translation lookups that,
because of a naming mismatch between what the code asks for
(`admin.config.add`) and what the newly generated dictionary actually
contains (`config.add`, missing its `admin.` prefix), now display literally
as `admin.config.add` on screen, in all nineteen languages including
English, for 244 separate pieces of text covering nearly every button,
heading, and error message on that page. That is a full, visible break of a
previously shipped and working feature, it was not caught before this round
was handed to Sentinel, and the project's own new documentation for this
round makes a promise — "a missing translation degrades to English, never to
a raw key" — that this exact bug violates. It is made worse by the fact that, partway through this review,
the project's own tracking documents were edited to call this feature
"Done" and to repeat the exact safety claim this review disproves — a status
that should not stand until the console reads correctly again. Per the
platform's own rule that a functional regression fails the round unless
someone with authority explicitly waives it in writing, and no such waiver
exists, the honest verdict is **FAIL**. Nothing here touches privacy or the platform's harder
promises, so this is a build-quality FAIL rather than a CRITICAL trust
violation — but it must be fixed, not waived, before this round can be
called done: regenerate `frontend/lib/i18n.generated.ts` so every `admin.*`
key carries its namespace prefix in all 19 locale blocks, then re-run
`bash tests/sentinel/i18n-key-check.sh` (now part of the permanent checklist)
until it passes.
