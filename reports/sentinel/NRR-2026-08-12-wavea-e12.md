## Regressions

### Finding 1 — FUNCTIONAL, moderate severity — dead App Store link for Jupiter in `docs/wallets.json`

`docs/wallets.json`'s Jupiter entry links iOS to
`https://apps.apple.com/app/jupiter-mobile/id6484069900`. That page returns
**HTTP 404** (confirmed both by `curl -L` against the live URL and
independently against Apple's public iTunes lookup API:
`https://itunes.apple.com/lookup?id=6484069900` → `resultCount: 0`). A search
against the same API finds the real app under a **different, adjacent** id:
`6484069059` ("Jupiter Mobile - Solana Wallet", Raccoon Labs Pte. Ltd.,
`https://apps.apple.com/us/app/jupiter-mobile-solana-wallet/id6484069059`) —
a 9-vs-05 digit transposition. Every other link in the file (Phantom iOS/
Android, Solflare iOS/Android, Glow iOS/Android, Trust Wallet iOS/Android,
Jupiter Android + web) resolved live (HTTP 200) at check time.

**Pre-existing, not introduced this round.** `git show
f4b92e6:docs/wallets.json` shows the identical wrong id was already present
at the base commit, before this round's edits. This round's wallets.json
changes (Glow gains an Android link, "Jupiter Mobile"→"Jupiter", the false
"mobile only" claim dropped) are correct and did not introduce the bug — but
they also did not catch it, because **no prior Sentinel round had an
executable link-liveness check**. `tests/sentinel/e12-wallet-check.sh`,
written this round, is the first to check it, and it is now a **committed,
regression-gated assertion**.

Per the Sentinel spec (Layer A, Onboarding/E9): *"every deep link resolves to
a live store page (a dead link for a discontinued wallet is a regression)."*
This is not the discontinued-wallet case, but the effect for a member is
identical: tapping "Jupiter" → iOS in the onboarding wallet chooser lands on
an Apple 404 page. It is not a privacy or Traditions violation (not
CRITICAL), and two of the wallet's three access paths (Android, web) still
work, but it is a genuine, currently-reproducible functional bug in a
shipped, user-facing flow, with no team waiver on file.

**Reproduction:**
```
bash tests/sentinel/e12-wallet-check.sh 2>&1 | grep 'DEAD LINK'
# -> ✘ DEAD LINK: jupiter (ios) -> https://apps.apple.com/app/jupiter-mobile/id6484069900 returned HTTP 404
curl -s "https://itunes.apple.com/lookup?id=6484069900" # -> {"resultCount":0,...}
curl -s "https://itunes.apple.com/search?term=jupiter+mobile+solana&entity=software&limit=5" \
  | python3 -m json.tool  # -> trackId 6484069059 is the real app
```

**First bad commit:** not cheaply bisectable in the usual sense — the wrong
id has been present since before `f4b92e6` and probably since the wallet was
first added to `docs/wallets.json`; whether Apple's id ever pointed
correctly at any commit, or the digit transposition is a copy/paste error
from day one, cannot be distinguished from the git history alone (the id
string itself never changed across its history in this repo). Not chased
further per the spec's "< 8 steps, cheap" bound — the fix is a one-line
value change (`id6484069900` → `id6484069059`), not a behavioural regression
to root-cause.

**Disposition:** FUNCTIONAL regression, no waiver on file. Per spec §3
("Functional regressions ⇒ FAIL unless explicitly waived in writing by the
team") this alone moves the round's verdict to **FAIL**. This is a one-line
data fix, not a design problem, and does not implicate any of this round's
new code.

### Finding 2 — QUARANTINED, pre-existing test fragility — `tests/epic2.ts`'s epoch-reinsertion test fails 3/3 in this environment

`anchor test --skip-build`'s full local-validator run (101 passing) fails
**consistently** — 3 out of 3 independent full-suite runs, all identical
failure point — on:

```
ayni — F54 recent roots / epochs + F56 fellowship anchor
  begin_member_epoch + reinsert_member: live members re-enter, expired do not, duplicates refused
  Error: AnchorError ... reinsert_member.rs:20 ... MembershipExpired (6001)
```

**Confirmed unrelated to this round's diff.** `git log -1 --
tests/epic2.ts` and `git log -1 --
programs/ayni/src/instructions/reinsert_member.rs` both point at commit
`9254f31`, three commits before this round's base (`f4b92e6`); neither file
appears in this round's `git status`.

**Root-caused by temporary instrumentation (added, verified, then fully
reverted — `git diff` confirms `tests/epic2.ts` and `Anchor.toml` are
byte-identical to the base commit after this investigation):** the test
configures a 2-second membership TTL, waits 1.5s after issuing the "live"
member, then calls `begin_member_epoch`, fetches two accounts, and expects
`reinsert_member` to still succeed. Diagnostic timers showed the client-side
elapsed time from issuance to the `reinsert` call was **~1.63s** of the 2s
budget — a ~370ms margin — before the `reinsert` transaction itself is even
sent and confirmed on-chain (which adds further, unaccounted latency against
the *validator's* clock, not the client's). In this 2-vCPU sandbox, that
margin is consistently insufficient. This is a **test-timing-margin
fragility**, not a logic bug in `reinsert_member.rs` — the program is
correctly enforcing expiry; the test's tolerance for RPC/validator latency is
too tight for this environment.

**Reproduction:**
```
anchor test --skip-build   # full suite; fails at the same point 3/3 in this sandbox
```

**Disposition:** per spec §3 ("Flaky tests are retried twice; still-flaky ⇒
WARNING with a quarantine entry that must be resolved within two rounds"),
this is entered as a **quarantined WARNING**, not treated as evidence this
round's changes broke anything (confirmed by the unmodified-file check
above). It must be resolved (either widen the test's timing margin, or make
the assertion time-independent by reading the validator's on-chain clock
instead of relying on client-side `setTimeout` budgets) within **two
rounds** of this one, or it escalates.
