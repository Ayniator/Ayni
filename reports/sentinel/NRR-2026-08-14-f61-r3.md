## Verification of the claims in the task brief

1. **Prior defect was real and correctly characterised.** Confirmed by reading
   `d6a4593:frontend/lib/visibilityCrypto.ts` — `profileEncKey(vk)` took the
   viewing secret alone (`SHA-256("aha-vis-enc-v1" ‖ vk)`), so the same member
   published byte-identical `enc_pub` in every Circle. The four documents named
   in the brief (`docs/visibility.md` §4, `docs/shipped.md`, `BACKLOG.md`,
   `tests/sentinel/checklist.yaml`) did previously carry this forward as a
   disclosed, deliberately-unfixed defect on exactly the "strands every
   published profile and key drop" rationale quoted in the brief — this is
   also independently corroborated by the prior round's own report
   (`NRR-2026-08-12-f60-f61-usability-reround.md` lines ~197–299, which lists
   it as an open coverage gap / disclosed defect).

2. **New domain tag confirmed.** `ENC_KEY_DOMAIN_V2 = "aha-vis-enc-v2"` is a
   genuinely new string, not `v1` reused with extra input.
   `profileEncKey(vk, circle) = SHA-256(tag("aha-vis-enc-v2") ‖ vk ‖ circle)`,
   with a hard `circle.length !== 32` guard so there is no accidental
   Circle-less call. Confirmed by direct read of the diff and of the resulting
   file.

3. **Write/read split confirmed by grep, not by trusting the comments.**
   `grep -rn "profileEncKey\|legacyProfileEncKey" frontend/ tests/` shows
   `legacyProfileEncKey` is called in exactly one place —
   `openMemberProfile` (the read path) — where it is used only to (a) test
   whether a fetched `MemberProfile.encPub` is the caller's own under the old
   rule, and (b) as a fallback shared-secret when hunting for a key drop
   addressed to the caller under the pre-fix derivation. Both call sites in
   `publishProfile` and `grantElementKeys` (the two write paths) call
   `profileEncKey(vk, circle.toBytes())` — v2 only. `legacyProfileEncKey` is
   never passed to `sealBio`, `sealElementKeys`, or any account-write
   instruction. A member cannot write under v1 after this commit.

4. **`myEncPub` signature change has no orphaned caller.**
   `grep -rn "myEncPub(" frontend/` finds exactly one hit — the function's own
   definition (`frontend/lib/visibility.ts:542`). It was already unwired to any
   UI page or component before this commit (confirmed by diffing against
   `d6a4593`, where it was equally uncalled) — this is a pre-existing,
   not-newly-introduced piece of unused API surface, not a regression, and
   noted below as a standing (not new) coverage note.

## Check-particularly items

- **Domain-tag freeze discipline.** Diffed `VIEW_DOMAIN`, `TAG_DOMAIN`,
  `OWNER_KEY_DOMAIN`, `ELEMENT_DOMAIN`, `DROP_DOMAIN`, `WRAP_DOMAIN` against
  `d6a4593` — byte-identical, untouched. `ENC_KEY_DOMAIN` ("aha-vis-enc-v1")
  is also untouched in value; only its comment changed to mark it
  legacy/read-only. Only one new constant, `ENC_KEY_DOMAIN_V2`, was added.
  `ownerTagFor`, `shieldedOwnerKey`, `elementKey` (definition), and
  `dropIdFor` are byte-for-byte unchanged — confirmed by
  `git show b082422 -- frontend/lib/visibilityCrypto.ts` showing no diff hunk
  touching those functions. **No silent baseline change** to any other
  derivation.
- **Legacy read must not leak into writes.** Verified above (item 3) — clean.
- **Privacy invariant, forward-looking.** For any *new* write, the derivation
  removes the cross-Circle linkage: `profileEncKey(vk, circleA) !=
  profileEncKey(vk, circleB)` for `circleA != circleB`, pinned by the new test.
  **Residual exposure, stated plainly:** any `MemberProfile.enc_pub` published
  *before* this commit lands and is upgraded stays on chain unchanged — and
  thus stays cross-Circle-linkable — until that member's next `publishProfile`
  call, which itself has a real cost (every existing key-drop grant to that
  member becomes unreachable at its old drop address and must be re-issued).
  This is **not automatic migration**; nobody is compelled to re-publish.
  Judged against the four documents: **all four state the residual honestly**.
  `docs/visibility.md` §4 explicitly says "the on-chain `enc_pub` of an
  existing profile is unchanged until the member next publishes" and spells
  out the re-issue cost. `docs/shipped.md`'s new F61-R3 section repeats the
  caveat under a "Not automatic, and worth stating plainly" heading.
  `BACKLOG.md`'s new entry says "Still open: ... an existing profile keeps its
  old global key on chain until the member re-publishes." `checklist.yaml`
  adds a dedicated "MIGRATION CAVEAT, still open" bullet, including a
  forward-pointing ask for a future round to verify members are actually
  migrating. None of the four overstates the fix as complete — this is a
  correctly-scoped, honestly-disclosed partial fix, not a silently-narrowed
  claim.
- **No chain/network import entered `visibilityCrypto.ts`.** Confirmed:
  `grep -n "^import" frontend/lib/visibilityCrypto.ts` returns exactly one
  line, `import nacl from "tweetnacl";`. No `@solana/web3.js`, no
  `@coral-xyz/anchor`, no `fetch`/`XMLHttpRequest`/`WebSocket`. The module
  remains pure-crypto by contract, as its own file-header comment requires.
  (`visibility.ts`, the orchestration layer one level up, legitimately does
  import chain/RPC — that is expected and pre-existing, not new.)
- **The new test is not vacuous.** `tests/epic5.ts` — "F61-R3: a member's
  profile key differs per Circle" — reimplements the v1/v2 derivations locally
  (the file's established, documented pattern: "copied on purpose rather than
  imported: if either side ever drifts, these tests fail") and asserts three
  independent, falsifiable properties: (a) `encKey(vk, circleA) !=
  encKey(vk, circleB)` for the same member — the headline property; (b) the
  legacy v1 key does not collapse onto the new v2 key for the same inputs

  `assert.deepEqual` against concretely computed byte arrays, not

## Verdict rationale

This round reviews one focused commit that fixes a privacy defect Sentinel
itself had flagged and carried forward as open in the previous round: a
member's public profile key used to be the same in every Circle they belonged
to, which let anyone linking two Circles' member lists re-identify the same
person across them. The fix makes that key different in every Circle from now
on, using a brand-new, frozen cryptographic label so nothing that already
exists on chain breaks — old profiles and old shared keys still work for
reading. The commit is honest that this is not a complete cure: anyone who
published their profile before this fix landed keeps the old, linkable key
until they publish again, and republishing has a real cost (previously granted
access has to be re-issued). All four places that describe this to a human —
the design doc, the shipped-features log, the backlog, and Sentinel's own
checklist — say that plainly rather than claiming the problem is fully solved.
I checked the code, not just the commit message: the new label really is new,
the old label is truly read-only now, no other cryptographic derivation was
disturbed, the module that must never talk to the network still does not, and
the new test genuinely proves what it claims rather than passing by default.
I then re-ran the entire regression suite from a clean local validator and got
the exact same "161 passing, nothing failing" result the commit claims, with
the new test included and green, and confirmed the type-checker is clean.
Nothing was found broken, hidden, or overstated. **Verdict: PASS.**
