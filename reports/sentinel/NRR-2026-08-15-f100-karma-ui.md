### 1. MEDIUM (test-rigor, not exploitable) — the commit's "removing the balance check turns the overdraft test red" claim is not reproducible; the test stays green for the wrong reason

- **Epic/feature:** F100 (`give_karma`), commit `b7695c2`.
- **What I did:** commented out
  `require!(from.points >= amount, AyniError::InsufficientKarma);` in
  `programs/ayni/src/instructions/give_karma.rs`, ran `anchor build`,
  redeployed to a fresh local validator, and re-ran the full `tests/karma.ts`
  suite.
- **Result:** **all 19 tests still pass**, including *"refuses a gift the
  giver cannot afford, WITHIN the cap — no overdraft"*. The transaction still
  fails — but the mocha assertion is a generic `try { } catch { threw = true
  }`, and it cannot tell *why* it failed. The transaction log shows:
  `Program log: panicked at programs/ayni/src/instructions/give_karma.rs:57:5:
  attempt to subtract with overflow` — a raw arithmetic panic from
  `from.points -= amount`, not the intended `InsufficientKarma` AnchorError.
- **Root cause:** this workspace's root `Cargo.toml` sets
  `[profile.release] overflow-checks = true`. That flag alone makes the raw
  `u64` subtraction panic on underflow, independent of the `require!`. It is a
  real, working, project-wide safety net — I confirmed with an isolated probe
  that the giver's balance and the receiver's balance are both **correctly
  left untouched** after the overdraft attempt, so **there is no live
  overdraft/mint exploit in the current code**. This is not a security
  regression.
- **Why it is still worth reporting:** the commit explicitly prides itself on
  having caught and fixed exactly this shape of defect one paragraph earlier
  — a test that "passes with the balance check deleted" because something
  else (there, the per-gift cap) rejected the transaction first for an
  unrelated reason. The same shape recurs here in a different guise: the test
  cannot fail for the right reason, because it doesn't check *which* error
  came back. If `overflow-checks` were ever turned off (a realistic future
  edit during a compute-budget pass), or if `from.points -= amount` were ever
  rewritten as `.saturating_sub(amount)` (a pattern already used two lines
  away for the receiver's `saturating_add`), the `require!` becomes the
  *only* thing standing between the current safe state and a real
  overdraft/mint, and nothing in the suite would notice it had gone missing.
- **Reproduction:**
  ```
  sed -i 's/require!(from.points >= amount, AyniError::InsufficientKarma);/\/\/ removed/' \
    programs/ayni/src/instructions/give_karma.rs
  anchor build
  ```

### 2. LOW/DOCS — `docs/karma.md` states something that is actually WRONG, not merely omitted

- *"It is not a record of who helped whom in any detail — only that some
  recognition passed between two members."*
- A `KarmaGift` PDA **is** exactly that record: it is seeded
  `["karmagift", circle, giver.commitment, receiver.commitment]`, carries
  `given_at`, and — because it is created with `init` and never closed even
  after a reclaim — is kept **forever**. Anyone who has (or brute-forces
  over) the two commitments can determine, in detail, who thanked whom and
  when. Per this same document and `KarmaCard.tsx`'s own comment,
  commitments are already treated as the enumerable "anonymous identity"
  this whole feature runs on.
- **Not re-raised as a Traditions/privacy CRITICAL**: this is the same
  enumerable-PDA shape already accepted for `KarmaAward`/`WingPeer` in the
  F97/F98 rounds ("Sponsor graph stays PRIVATE... pre-existing F27 WingPeer
  PDA enumerability... not deepened"), and the 2026-08-15 karma waiver
  already accepts full public comparability of totals. But the docs text
  specifically *denies* that a who-thanked-whom detail exists, and it does —
  member-facing copy being wrong about what a feature reveals is worth
  fixing even though the underlying architecture is an accepted tradeoff.

## Karma economics — adversarial summary (task items a–d)

- **(a) Try to break the "once per ordered pair, ever" bound.** Reproduced on
  a local validator:
  - *Close/reopen the `KarmaGift` account:* statically impossible — grepped
    the whole program for any `close =` constraint or instruction touching
    `KarmaGift`; none exists. There is no code path to reopen it, not merely
    an unused one.
  - *Reclaim then re-gift:* covered by the shipped suite (`tests/karma.ts`,
    "and the pair still cannot gift again after a reclaim") — refused,
    reconfirmed.
  - *Three-member ring, A→B→C→A, with `gift_return_secs` voted to 0 first*
    (so every leg is immediately reclaimable): the ring itself conserves
    total karma (pure transfers). The three subsequent reclaims mint exactly
    **300** (= 3 distinct ordered pairs × the 100 cap) — this is **not** a
    violation of the disclosed bound, it is the bound acting on three pairs
    at once, exactly as the commit's own reasoning ("bounded by how many
    distinct people chose to thank them") predicts. Re-gifting any leg again
    after its reclaim was correctly refused.
  - *Same pair, a second Circle:* allowed, by design — `Karma`/`KarmaGift`
    are seeded per-Circle, and the program's own comment states karma is
    "a Circle-local quantity" deliberately. Not a bypass of the bound; a
    different, independent bound (per Circle the pair shares).
  - *`end_wing_peer` / re-linking interaction:* not applicable — that
    machinery only touches `WingPeer`/`KarmaAward` (F98), never
    `KarmaGift`/F100; confirmed by grep (no cross-references).
- **(b) No overdraft.** See Regression 1 — no live exploit, but the
  mutation-testing claim in the commit message is not reproducible as
  stated.
- **(c) `bump == 0` default-materialisation completeness.** Re-checked all
  three writers of `KarmaParams` (`establish_wing_peer.rs`'s and
  `give_karma.rs`'s bump==0 blocks, `set_karma_params.rs`'s votable-write
  block): all three now write every field (`gain_sponsee`,
  `sponsor_ratio_bps`, `min_sponsors`, `max_gift`, `gift_return_secs`,
  `bump`). No remaining partial-init path found — this is the exact defect
  class the commit discloses fixing, and the fix is complete.
- **(d) `reclaim_karma` permissionless / one-shot / period-at-reclaim-time.**
  Destination (`giver_karma`) is seed-bound to `giver_membership.commitment`,
  not an argument — cannot be redirected. `returned` is set before anything
  else and the account is never closed — cannot be replayed (test +
  independently reconfirmed). Reading the period at reclaim time was
  specifically exercised by the ring probe above (vote the period to 0,
  *then* gift, *then* mass-reclaim) and found no additional abuse beyond the
  disclosed, bounded mint.

## Verdict rationale

This round shipped two unrelated features in one commit: a way to thank a
fellow member with a small amount of karma that comes back to you but stays
with them, and a much larger set of daily reflections in three languages.
Neither one broke anything that used to work, and the specific way the karma
system could theoretically be gamed — passing thanks around a circle of
friends to inflate everyone's numbers — turns out to be bounded exactly the
way the commit says it is: each pair of people can only do this once, ever,
in each direction, and no amount of cleverness with closing accounts,
reclaiming early, or forming a ring of three found a way around that. The
reflections content was checked end to end and every single day of the year
shows something real in English, French, and Spanish. The one thing worth
real attention is that a test meant to prove "you can't give away karma you
don't have" doesn't actually prove that on its own — a safety net elsewhere
in the program happens to catch the same mistake, so nobody is at risk today,
but the test would not warn anyone if that safety net were ever removed. A
few small things in the written documentation and the project's own
bookkeeping (a wrong sentence about privacy, a duplicated line, two missing
entries in the shipped-features list) are easy to fix and do not affect
members using the app today.
